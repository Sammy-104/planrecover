# Notification delivery and outcome setup

The SES email sender, SNS outcome receiver, browser push lifecycle and encrypted push adapter are implemented independently of Bedrock. All activation flags remain off. No AWS topic, public ingress, VAPID keys or push subscriptions were provisioned by this change, and no live message was sent. The private Site audience and the existing restricted SES sending permission are unchanged.

## SES outcomes

`POST /api/webhooks/ses` accepts original Amazon SNS envelopes only when `AWS_SES_EVENTS_ENABLED=true`, `AWS_SES_REGION` and the exact `AWS_SES_EVENTS_TOPIC_ARN` are configured. It requires SNS signature version 2, validates RSA/SHA256 with the X.509 certificate fetched from that region's exact SNS HTTPS host, rejects redirects and nonstandard certificate paths, checks timestamps, and bounds request/certificate sizes. At most 16 certificate entries are cached for one hour. It never follows subscription confirmation URLs. Confirm a deliberately created subscription in AWS using the authenticated console.

Configure an SES configuration set to publish Delivery, Bounce, Complaint, DeliveryDelay, Reject and Rendering Failure events to the exact SNS topic. Set `AWS_SES_CONFIGURATION_SET` on the existing sender. The topic policy should allow SES publishing only for the intended AWS account and configuration set. Require SNS signature version 2 on the topic. An SES acceptance MessageId alone is not delivery evidence.

The receiver binds `PlanRecoverAttempt` email tags, the provider MessageId, region and single recipient hash to a durable `aws-ses/send-email` attempt. It deduplicates by SNS topic and event MessageId. Unknown attempts are acknowledged without retaining unrelated mail. Only event type, coarse reason, scope, timestamps, provider MessageId and digests are stored; email headers, bodies and recipient addresses are discarded. Coarse personal evidence is available through `GET /api/plans/:planId/me/notification-outcomes`, which requires current plan membership.

Permanent or undetermined bounce and complaint create permanent suppression for that owner's recipient hash across plans. A transient bounce creates a 24-hour cooling period. A later delivery event never removes suppression. Both the reminder runner and SES dispatch fence check suppression before sending. Opt-out, removed membership, deleted/changed plans and changed destinations still prevent dispatch. Suppression does not change a member's private reminder preferences or retry an accepted/uncertain message. Permanent suppression requires a deliberate operator review; there is no automatic clearance endpoint.

**Private ingress still needs operator setup.** SNS cannot call a private Site gateway directly. Keep this Site private. Use a deliberately deployed minimal relay or authenticated AWS delivery integration that forwards the original envelope, retaining its SNS signature and fields, through the existing private gateway's supported authorization mechanism. Grant/rotate any relay credential explicitly. Provisioning that ingress and verifying genuine callbacks are operational work remaining; local signed fixtures are not evidence of AWS delivery.

## Browser push

`GET/POST/DELETE /api/plans/:planId/me/push-subscriptions` require a signed-in owner/editor with current membership. Mutations require the app origin. Registering requires explicit confirmation and a valid browser subscription: P-256 ECDH public key, 16-byte auth secret, future expiration (or null), and an HTTPS endpoint on an allowed push service. The API returns device metadata and the public VAPID key only; endpoints and auth keys remain private server data. Revoking and expiration erase stored endpoint/key material.

The allowlist covers FCM, Mozilla, Apple and Microsoft push endpoints with fixed host/path rules. IP addresses, private networks, arbitrary callback hosts, embedded credentials, nonstandard ports, query/fragment URLs, redirects and malformed keys are rejected. Browser subscriptions are capability secrets: do not log, export or share them. This version allows three active devices for a member's plan. A browser endpoint can belong to one plan/account at a time; remove its prior registration before moving it. The UI provides registration/removal without requesting browser permission on page load. Removal stops server dispatch even if the browser retains its permission.

Provide a dedicated `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY` and `WEB_PUSH_SUBJECT=mailto:...` in private runtime settings; leave `WEB_PUSH_ENABLED=false` while preparing them. The browser must subscribe with that same public key. Use a vetted VAPID key generator and keep the private key outside source control. The installed `@block65/webcrypto-web-push` 2.0.0 builds standard RFC 8291 `aes128gcm` encrypted messages with RFC 8292 VAPID authorization; custom encryption is not implemented here.

After owner activation, delivery still requires each member's `delivery.push` preference and an active registered browser. The existing background runner selects the standard browser adapter when `WEB_PUSH_ENABLED=true`. A durable per-job/per-device attempt is committed before dispatch, and membership, preference/source versions, subscription version, expiration and the job lease are checked immediately before the request. Unknown responses and interrupted attempts require review and never automatically resend. Definite rejections are retained for review; 404/410 expire the subscription and erase its capabilities. Browser-reported expirations are cleaned during the next owner push run. All calls use an eight-second deadline and reject redirects.

Pushes contain a generic notice and `/flows`, with no plan names, balances, receipt or personal details on the lock screen. `public/sw.js` validates the message, displays it and opens only the app's own `/flows` URL. Service-worker subscription changes ask open pages to refresh registration; no auth credential is stored in the worker. Push-service 201/202 acceptance does not prove device display. Verify a real supported browser, permission denial, revocation, subscription renewal and expiration before enabling unattended delivery.

An explicit `AWS_SES_ENABLED=false` prevents email from falling back to the generic adapter. An explicit `WEB_PUSH_ENABLED=false` likewise blocks generic push fallback. Omitting these flags preserves the legacy generic provider contract; enabling a dedicated adapter selects that adapter. Never enable a live channel merely to make readiness appear configured.

## Offline verification

Run `node scripts/test.mjs backend-ses-outcomes backend-web-push backend-ses-email backend-reminders backend-adapters`. SNS fixtures use an in-memory synthetic RSA key and certificate, and the push fixture independently decrypts the actual library ciphertext using the browser's generated ECDH key. Tests cover signature/recipient binding, SSRF, replay, suppression, opt-out and membership races, expired subscriptions, durable attempts and ambiguous-send prevention. The test runner blocks live network access.
