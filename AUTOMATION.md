# PlanRecover saved-payment checks and reminders

Run the deployed updater hourly in America/Toronto, the minimum interval supported by Sites scheduling. The Settings button also runs checks on demand. This is the private PlanRecover Sandbox Site linked to this source. Routine runs update its database without rebuilding or publishing source.

1. Use Sites `get_site` for the linked Site. Preserve its owner-only audience. Obtain its supported service access from `siwc_bypass_bearer_token` in memory. Never place credentials in task prompts, command arguments, logs, source, URLs or files.
2. Send an empty JSON object to `POST /api/jobs/scheduled` on that returned live Site origin. Supply the same service token in `OAI-Sites-Authorization: Bearer …` for the private gateway and `Authorization: Bearer …` for the separately configured backend runner. The backend's secret `JOB_RUNNER_KEY` was configured to match this Site's service token. A service request does not impersonate a signed-in visitor.
3. The linked source helper `scripts/run-hosted-background-jobs.mjs` accepts `{url,token}` through hidden stdin and prints only processing counts. It pins this Site's exact live origin, refuses redirects and uses a deadline. Equivalent HTTPS calls may use the same supported headers. Send no owner, plan or provider payload.
4. Read persisted confirmation with Sites `read_database_overview`, then `read_database_table_rows` using the exact returned binding and `background_job_runs` table name. Follow only returned pagination offsets if needed. Match a run's `last_started`/`last_completed` to this invocation and inspect status. If `processed` is zero, existing leases or cooldowns can explain an idle run; do not reset them or invent success.
5. The updater selects one saved workspace per run fairly by last attempt. It recovers at most one lost approval-order identity with its original immutable request and unexpired key; reads up to five unresolved payment outcomes and two invoices; completes up to five already-approved, already-confirmed cancellations; synchronizes ten plans using a persisted cursor; and delivers up to one hundred due in-app reminders. Leases, cooldowns, current plan/member checks and unique financial effects fence retries.

The updater cannot capture a payment, issue a refund, send an invoice or approve a proposal. These actions require their existing reviewed user flows. The optional external notification adapter is disabled unless configured; delivery additionally requires a current explicit recipient opt-in and confirmed private destination. It uses stable delivery keys and bounded retries. The updater also cleans abandoned tracked receipt sources after 30 days while retaining reviewed/referenced evidence. Pending refunds never become available cash. Supplier evidence remains owner-confirmed and time-limited; no live inventory is asserted.

For 401/403, missing configuration or rotated service access, report that the runner credential needs refreshing. Do not broaden the audience, append credentials to a URL, provision AWS resources or switch payment environments. On a provider or storage failure, retain saved evidence and let a later bounded run retry. Report only a meaningful failure or a user action required; stay quiet on unchanged successful checks.
